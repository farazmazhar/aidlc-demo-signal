# Requirements Analysis — Questions

## Sources

- [desc] Initial description: "poc Build Signal, a customer feedback triage tool for early-stage product teams. Users submit feedback through an API or a web form. Each item is classified by an LLM for category, sentiment and urgency, and embedded for similarity. A weekly scheduled job clusters feedback into themes and writes a short summary of what changed and what needs attention. A dashboard shows themes, trends, urgent items, and lets users drill down to the raw feedback. Constraints: the system must run fully locally against an AWS-compatible emulator (endpoint http://localhost:4566) with no cloud spend. Target AWS services are API Gateway, Lambda, DynamoDB, EventBridge Scheduler and SES, with Postgres/pgvector for vectors. The LLM and embedding provider must be swappable between Ollama (local) and Amazon Bedrock by configuration only. Infrastructure must be defined as code and deployable to the emulator."

## Q1. What should the LLM classify each feedback item against?

The description fixes the three axes (category, sentiment, urgency) but not the values, and the values decide both the prompt and what the dashboard can filter on. Anything else is a free-form label the LLM invents, which makes trends and filters unstable.

- A. Fixed small enumerations: category in {bug, feature request, usability, performance, pricing, other}; sentiment in {positive, neutral, negative}; urgency in {low, medium, high}. Stored as strings and used verbatim by the dashboard filters.
- B. Category and urgency free-form short labels generated by the LLM; only sentiment fixed to {positive, neutral, negative}.
- C. Two-level urgency (urgent / not urgent) and a fixed category list, with sentiment free-form.
- D. Not yet defined — the schema will be decided while implementing the prompt.
- X. Other (please specify)

[Answer]: A

## Q2. What does a submitted feedback item contain, and is ingestion authenticated?

This is the API and web-form contract, and it decides the DynamoDB item shape and what the classifier can see beyond the text.

- A. Minimal and identical for both entry points: `source` (api|web), `text`, and a server-side timestamp; optional `submitter_email` and `product_area`. No authentication on either path (local spike only).
- B. Minimal payload plus a shared API key header on the API path; the web form stays unauthenticated.
- C. Richer payload: also `product_version`, `plan_tier`, and a client-supplied `submitted_at`, so feedback can be segmented.
- D. Not yet defined.
- X. Other (please specify)

[Answer]: A

## Q4. What non-functional bar should the spike meet?

A spike can legitimately have almost no NFR targets, but the requirements artifact needs the bar stated so nobody invents one later.

- A. Local responsiveness only: classification plus embedding returns within a few seconds for a single item, and the weekly job over a few hundred items finishes in minutes. No concurrency, availability or durability targets.
- B. A stated volume floor and latency numbers: seed the spike with a fixed corpus (specify the size in Other if you have one) and require the weekly job to complete within a few minutes at that size.
